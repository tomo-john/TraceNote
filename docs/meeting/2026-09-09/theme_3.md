# UIコンポーネント

## なぜコンポーネント化したか

1. UIの統一性

同じようなボタンや入力フォームを各Bladeに個別で書くと、

- classの指定が微妙に違う
- 修正漏れが発生する

などで、画面ごとに差が生まれる可能性がある。

2. 修正箇所の集約

共通コンポーネントを修正することでそのコンポーネントを使用しているすべての画面に変更を反映できる。

3. 再利用性

同じUIを複数の場所で利用できる。

## どのようなUIを共通化したか

基本ディレクトリ構造:

```bash
resources/views/components
    |----layouts: ベースレイアウトファイル
    |       |---- 共通ヘッダー・フッター
    |
    |----ui: 共通コンポーネント
    |----trace: trace関連のUIコンポーネント
    |----tag: tag関連のUIコンポーネント
```

共通化したUI:

- button
- card
- dropdown-item
- empty-state
- error
- input
- link
- logo
- modal
- nav-link
- select
- status-badge
- tag-badge
- textarea
- toast

=> 資料では一部抜粋して代表例をいくつか見せる

## 共通化する必要性を感じたこと

開発を進めて画面が増えるにつれて、UIを個別に実装した場合は修正箇所も増えていくと考えた。

初期段階ではまず各画面の機能と最低限のUIを実装し、その後共通化できる部分を見直してコンポーネント化する方針で開発を進めた。

## コンポーネント化した結果

- 同じコンポーネントを利用することでUIの統一性を保ちやすくなった
- 共通のUIの修正をコンポーネント側に集約できるようになった

## ここで学んだこと

どの部分までをUIコンポーネントと切り分けるかを意識することができた。

同じUIを複数の場所で使用する場合でも、すべてをコンポーネント化するのではなく、

再利用性や役割を考えて切り分ける必要があると学んだ。

コンポーネントに属性や変数を渡し、同じコンポーネントでも表示内容を変えられることを学んだ。

## memo
